# stale-monitors

**Do safety monitors survive fine-tuning? Refusal and persona directions as regression signals in open-weight models.**

CS 7150 term project (Fall 2026) and open research. Pre-registration: [`prereg/PREREG-v0.2.md`](prereg/PREREG-v0.2.md) (draft v0.2; frozen in git before the first measured run, filed on OSF by the owner). v0.2 supersedes v0.1: it replaces the condition 3 data after a licensing check, fixes the sampling rule for the free-form evals, adds the reworded-prompt ladder battery for H5, and scores H6 at the base operating point.

## Abstract

After LoRA fine-tuning of an open-weight chat model, how much do activation monitors fitted on the base model (the refusal direction, a refusal subspace, persona vectors for evil, sycophancy and hallucination, and linear harmful-vs-harmless probes) lose, does the white-box drift they read predict behavioral safety regression, and does persona drift explain refusal loss? We answer this with a controlled, within-base comparison. For each of four bases (Qwen/Qwen3.5-9B, Qwen/Qwen3.8-27B, google/gemma-4-12B-it, google/gemma-4-31B-it, each at a pinned revision, text decoder only, thinking disabled) we train a bank of 16 LoRA derivatives under six data conditions: benign domain SFT, persona-shifting benign data generated by the base, the Apache-2.0 trait-eliciting fine-tune sets of the persona-vectors paper plus one self-generated risky-financial-advice set, strong narrow misalignment (insecure code), detection-only safety removal, and controls. We measure behavioral safety on every derivative with fixed batteries (including the reworded-prompt ladders of Karne 2026) and two pinned judges from different families, measure capability (MMLU, IFEval) for the pre-registered exclusion, and measure white-box drift relative to the base with pre-declared metrics (D1 to D3, per-monitor delta-AUROC, persona projection shift, adapter projection, recall at the base 1%-FPR threshold before and after label-free realignment). Six pre-registered hypotheses (H1 to H6) cover monitor staleness, drift as a predictor of confirmed regression, persona versus refusal drift, prompt-extracted versus organism-extracted vectors, the change in compliance-stratified recall after fine-tuning, and label-free realignment at the base operating point. Null results are published as such.

## Install

Python 3.12.

```bash
python3.12 -m venv .venv
.venv/bin/pip install -e "code[test]"      # the sm package plus pytest
.venv/bin/pip install -e "code[serve]"     # optional: vLLM, for judge serving and persona generation on GPU
```

On Explorer the `monitors` conda env (`/projects/interpretability/shehral.m/conda_envs/monitors`, torch 2.13.0+cu130 with vLLM 0.31.0) is built by `jobs/env_build.sbatch`; do not pip-install into a login-node environment. GPU jobs need the CUDA forward-compatibility library on `LD_LIBRARY_PATH`; see [`docs/RUNBOOK.md`](docs/RUNBOOK.md).

No script downloads anything unless `--allow-download` is passed, and nothing downloads when `SM_OFFLINE=1` or `HF_HUB_OFFLINE=1` is set. Cluster jobs run offline against a pre-filled cache (`jobs/download.sbatch`).

## Tests

From the repository root:

```bash
SM_OFFLINE=1 .venv/bin/python -m pytest tests -q -p no:cacheprovider
```

With `SM_OFFLINE=1` the fixtures build a tiny random Qwen3-style model from a config, so no network is touched and no weights are downloaded. Tests run on CPU only (MPS is never used) and at most two pytest processes may run at a time on the laptop. `SM_TINY_MODEL` overrides the tiny model (a Hub id, or a local directory when offline). Details in [`tests/README.md`](tests/README.md).

## Running the study on Explorer

The stage sequence for each base is:

1. environment build and downloads at the pinned revisions (CPU, proxy on),
2. tiny-model smoke on `gpu-short` that loads the real base through the same loader call and revision as the measured stages (gate G1),
3. prompt sets and bank datasets (built once; persona and risky-advice data per base),
4. base card per base (directions, probes, persona vectors, frozen monitor thresholds and declared drift score),
5. V4 causal validity check, a hard gate: a base without a passed V4 file gets no further GPU stages,
6. LoRA bank training (array over `configs/bank_<base>.yaml`),
7. batteries for the base and every derivative (adapters unmerged),
8. capability scores (MMLU, IFEval) for the base and every derivative,
9. judging: J1 on all items, J2 on 10% of every derivative,
10. J2 re-score of 100% of the harmful items of every J1-flagged derivative and of the base,
11. drift metrics per derivative,
12. per-item monitor scores on every battery, including the ladders,
13. aggregation into bank tables and H1 to H6 evaluations.

SLURM templates, partitions and flags are documented in `jobs/README.md`. The step-by-step procedure for one base, with commands, output paths, the revision pins, expected H200-hours, the CUDA notes and the fallback procedure for a base that fails to load, is [`docs/RUNBOOK.md`](docs/RUNBOOK.md). Gates before measured runs (smoke test, frozen pre-registration, daily budget, failure streak) are listed in [`docs/PLAN.md`](docs/PLAN.md).

## Hazards: what is never released

Per pre-registration Section 8 and the harness spec:

- **Ablated weights.** Condition 5 directional ablation is applied in memory at read time and never saved or uploaded.
- **New misalignment recipes.** Nothing harmful is trained from new recipes. The condition 3 self-generated risky-financial-advice set and the system prompt that elicits it are kept out of the release (hashes only) unless the owner decides otherwise and logs it.
- **Harmful response texts.** Completions for the harmful batteries (StrongREJECT, HarmBench, XSTest unsafe, and the harmful Karne ladders) are stored only under `results/restricted/` (directory mode 0700) and are published as SHA-256 hashes only. Judge labels for those batteries live in the judge output's own `restricted/` directory. The causal check never writes completion texts.
- **Credentials.** Hugging Face tokens and other secrets stay out of the repository (`.env` is gitignored).

LoRA adapters are not on the pre-registered publication list; any release of adapters is an owner decision recorded in the deviations log.
