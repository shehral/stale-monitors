## 1. Running accept.py

- **Where.** The laptop checkout, which holds the authoritative git history and `prereg/DEVIATIONS.md`. First pull additively from the cluster: `results/` (including `results/restricted`, kept 0700), the stage's job logs into `logs/` (git-ignored, 0700), `data/prompts/MANIFEST.json`, `data/bank/MANIFEST.json` and `$SM_PROJ/.compute_budget.json`. Only this checkout runs `--write`; any other ledger copy is a mirror.
- **CLI.** `python -m sm.accept --stage <stage> --base <key> [--run <run_id>] --job <raw id | arrayid_task | local> [--write]`, plus `--verify-ledger` (exit 0 when the prefix witness holds and every row parses, else 20). [v0.2 of the rubric] A pooled aggregate takes `--base all`; `--run` is required for lora, organism, judge_j1, judge_j2 and drift; `--root` names another checkout and `--agg-config` the AGG_CONFIG of a local aggregate run. [v0.2 of the rubric] Stages, in pipeline order: `smoke, base_card, causal, lora, organism, battery, capability, judge_j1, judge_j2, drift, monitor_scores, aggregate`. `organism` was not in the original stage list; `jobs/README.md` added it between lora and battery on 2026-10-07.
- **No model, GPU or network access.** accept.py uses only the stdlib, numpy, pyyaml, git, the pure functions `sm.eval.judge.wildguard_template_sha256` (`granite_template_sha256` before rubric v0.4.8), `sm.analysis.stats.wilson_interval` and `sm.analysis.aggregate.DEFAULT_CONFIG`, and the pure module `sm.analysis.rules` (inside the freeze; J2-3 and J2-4 re-derive the J2 status with it). [v0.3 of the rubric]
- **Report.** Written to `results/acceptance/<stage>/<base>/<run or _>.<slurm_job_id>.json` with {stage, base, derivative, slurm_job_id, outcome, failure_class, checks [{id, passed, detail}], triggers [{id, covered_by}], ledger_row}. The report is written with or without `--write` and also carries rubric_version, warnings (DEVIATIONS.md parse problems), blocks_on_reject, freeze_row, and each trigger's value and source. [v0.2 of the rubric] It also lists `outputs` ({path: SHA-256}, which hashes to the row's output_hash) and, with `--write`, is saved with `append_pending: true` before the rows are appended and with `written: true` after (2.5). [v0.3 of the rubric] `--write` also appends the ledger row (2.5) and updates `.failure_streak.json` (2.2). Reports, rows and stdout never quote completion or judge text.
- **Exit codes.** 0 ACCEPT; 10 ACCEPT WITH DEVIATION; 20 REJECT; 2 usage or internal error (never an outcome). The next stage is submitted only after 0 or 10.
- **Logs.** `logs/<prefix>-<jobid>.out|.err`, with the sbatch `--output` prefixes (smoke, base-card, causal, lora, battery, capability, judge, drift, monitor-scores, aggregate); array jobs use `<prefix>-<array>_<task>`. The closing line `LEDGER job=<raw id> array_job= task= name= gpus= elapsed_s= rc=` gives the raw SLURM id and the rc; a log without it is incomplete (infrastructure). A laptop aggregate run has no log; its id is `local-<hypotheses.json meta.timestamp>`.
- **Tests.** `tests/test_accept.py` builds one passing synthetic tree per block, then applies one mutation per check id, and asserts the outcome, the failure class and the failing id. No models.

## 2. Rules for every stage

### 2.1 Common checks C1 to C11 (they apply inside every block)

- **C1 Pins.** Pin(base) = `configs/bases.yaml` `bases.<base>.revision` (40 hex). The stage config's top-level `revision` equals Pin (the `sm_py config-rev` rule). Every base revision an output records (fields named per block) equals Pin. `configs/judge.yaml` `j1`/`j2` `model` and `revision` equal `bases.yaml` `judges.J1`/`judges.J2`. A kind-model run records its manifest `external_revision` (40 hex). After the freeze row exists, the four primary pins and two judge pins must equal the ones it hashed; otherwise trigger `pins_change`.
- **C2 Code.** The job log has `frozen: base=<base> pin=<Pin> commit=<40 hex>` (`sm_require_frozen`; for aggregate, use hypotheses.json `meta.git_commit`), and its base is `--base` [v0.2 of the rubric]. That commit is the row's `git_sha`. It resolves locally (`git cat-file -e <sha>^{commit}`, else precondition) and equals `meta.git_commit` of every JSON output that carries one; an output from another commit (an idempotent skip over an older output) is precondition: re-run with FORCE=1. [v0.2 of the rubric]
- **C3 Smoke (G1).** Some accepted smoke row for the same base (any base, for aggregate) has a `git_sha` whose `code/` and `jobs/` trees (`git rev-parse <sha>:code`, `<sha>:jobs`) equal this row's. [v0.3 of the rubric] Otherwise re-run the smoke. (configs/ is not bound here: C1 and the blocks check config values.)
- **C4 Hashes.** `output_hash` = SHA-256 of the UTF-8 text made of the sorted lines `<repo-relative path>\t<sha256 of the file>\n` over the block's outputs for the unit. Internal hashes must verify: `completion_sha256` = SHA-256 of the completion's UTF-8; battery `output_sha256` = SHA-256 of the JSONL bytes; direction `vector_sha256` = SHA-256 of the little-endian float32 vector; `adapter_sha256` = SHA-256 of `adapter_model.safetensors`. Each entry of an output's input-hash map (`input_sha256` or `inputs_sha256`) equals that file's SHA-256 now; map cluster paths by stripping `$SM_PROJ/` (default `/projects/interpretability/shehral.m/monitors/`) and skip HF-cache paths. Map keys that are names rather than paths (no `/`, no file suffix) are checked by the block that knows them; a `data/bank/` or `data/prompts/` file that was not pulled is compared with its MANIFEST entry instead; any other input that is not present locally is precondition (pull it). [v0.2 of the rubric]
- **C5 Seeds.** The seed fields named in each block are integers equal to the config or manifest value. The row's `seeds` object holds them.
- **C6 H200-hours.** `.compute_budget.json` `by_day.*.jobs[]` has an entry with `slurm_id` = the raw id and `elapsed_hours` (elapsed x allocated GPUs; 0 for CPU jobs). The first ledger row of a `slurm_job_id` carries that value; later rows of the same id, and local runs, carry 0.0 (the analysis_freeze row does not count as a first row). [v0.2 of the rubric] A day above `soft_cap_h200_hours_per_day` is noted, not rejected (G4 is enforced at submission).
- **C7 Hazards (prereg Section 8).** Harmful batteries are the `configs/batteries.yaml` entries with `harmful: true`: strongreject, harmbench, xstest_unsafe, karne_ladders, karne_ladders_sens, karne_ladders_sampled_base (the base only; fidelity review N7, prereg v0.3 change 54). Restricted batteries, whose outputs and label files (a) and (b) govern, are the harmful ones plus every entry with `restricted: true` (OPEN-3: em_freeform and persona_*), every battery `data/prompts/MANIFEST.json` marks `harmful` or `restricted`, and the name rule of `sm.eval.battery.is_restricted` (the harmful names and their `_`/`-` prefixes, em_*, emergent_*, persona_*; accept.py keeps a mirror that a test compares with it). [v0.2 of the rubric]
  - (a) Every battery output (`.jsonl`, `.jsonl.partial`) and every judge label file of a harmful battery resolves (realpath) under `results/restricted/`, with every directory from `results/restricted` down to it at mode 0700 and the file at 0600.
  - (b) No file outside `results/restricted/` holds a harmful-battery row with a `completion` or `raw` field.
  - (c) Leak scan: for every harmful-battery row whose J1 label is `harmful_compliance`, every em_* row labelled `misaligned` and every persona_evil row labelled `trait_expressed` (OPEN-3) [v0.2 of the rubric], and whose completion (whitespace collapsed) has at least 80 characters, its first 80 characters must not occur (fixed-string search, on the whitespace-collapsed text and as a JSON-escaped string) in any file under `results/` outside `results/restricted/`, nor under `paper/`, `docs/`, `artifacts/`, `to_human/`, `prereg/`, `jobs/`, `literature/`, `code/`, `configs/` or `tests/`, or in any top-level file of the checkout. [v0.3 of the rubric] Each file is searched as whitespace-collapsed text, after undoing JSON escapes (`\n`, `\t`, `\uXXXX`, ...; with and without CSV doubled quotes), and (`.json`, `.jsonl`) value by value, so a completion with a newline in its first 80 characters stored with `json.dumps` is found. [v0.3 of the rubric] An archive (`.gz`, `.zip`, `.tar`, ...) under `results/` outside `results/restricted/` cannot be scanned and fails C7c. [v0.3 of the rubric] `logs/` and `data/` are never scanned (`logs/` is git-ignored, 0700, and holds judge prompts by design; `data/` holds training data that a derivative may reproduce). [v0.2 of the rubric]
  - (c, continued) [v0.4.2 of the rubric, D-003, 2026-10-09] An 80-character prefix shared by two or more distinct restricted rows (different items or samples) is a stock opening of the model, not evidence that one specific completion was copied; such a prefix is searched as the first 200 collapsed characters of each of its completions instead. Unique prefixes are searched as before. Found on the first bank: one opening shared by 14 restricted (run, battery) pairs matched 74 benign XSTest-safe answers of the same derivative.
  - (c, continued) [v0.4.3 of the rubric, D-005, 2026-10-09] Files under `results/batteries/` (the open batteries: a model's answers to benign prompts) are searched for the whole collapsed text of each flagged completion rather than its prefix, because a templated derivative opens its benign and harmful answers identically (80 identical leading characters against a benign prompt cannot carry the harmful request's specifics). Every other target keeps the prefix rule of v0.4.2.
  - (c, continued) [v0.4.4 of the rubric, D-007, 2026-10-09] Recorded redaction. When a flagged completion is found in an open battery file, `sm.ops.quarantine` moves the row's original text to `results/restricted/batteries/<base>/<run>/<battery>.quarantine.jsonl` (0600), replaces the open row's `completion` with `[REDACTED: restricted; sha256=<sha256 of the raw original>]` and sets `redacted: true`, keeping the row's original `completion_sha256`, and records in the sidecar a `redaction` block {n_rows, rows, output_sha256_before, output_sha256_after, quarantine_file, deviation, tool, timestamp} with `output_sha256` set to the new file hash. Every hash check (BT-1, BT-2, C4 input maps, J1-5, J1-9, J2-7, CP-3) accepts a file whose current hash equals `output_sha256_after` and whose recorded hash equals `output_sha256_before`; a redacted row is explained when the marker's hash equals its `completion_sha256`. Earlier ledger rows are never changed; a battery re-accepted after a redaction cites D-007 in its note. Records carry hashes, row ids and repo-relative paths only, never text.
  - (c, continued) [v0.4.5 of the rubric, D-009, 2026-10-09, owner decision] Files under `results/batteries/` are not leak targets: a derivative's answers to benign prompts are releasable even when identical to its judged-harmful answers (the owner: release as such papers traditionally do). The prefix rule of v0.4.2 still applies to every other target (tables, docs, paper, tests, top-level files). The recorded-redaction mechanism of v0.4.4 remains available but is not exercised on this bank.\n  - (c, continued) [v0.4.6 of the rubric, D-011, 2026-10-09] `results/monitor_scores/` is not a leak target: its files hold per-item monitor projections and thresholds computed from prompts and activations and never contain generated text; scanning them (tens of MB) against the tens of thousands of flagged completions of a judged bank made each acceptance take about fifteen minutes.\n  - (d) Weights: under `results/`, no `*.safetensors`, `*.bin`, `*.pt` or `*.gguf` except `results/adapters/<base>/<lora run_id>/adapter_model.safetensors`, and no `results/adapters/<base>/c5_*`.
  - (e) No JSON written by base_card, causal, organism, drift or monitor_scores has a key named completion, completions, response or responses.
- **C8 Freeze.** After the freeze row exists (2.4), `analysis_sha` computed now equals the frozen value, or a value named by a covered `analysis_code_change` entry (the outcome is then ACCEPT WITH DEVIATION). The `code/sm/analysis` tree at the job's own commit (C2) must also equal the frozen tree, else `analysis_code_change` fires with that tree as its value, as in AG-2 (a job runs the J1 flag and J2 status rules of its own commit); a tree that does not resolve is precondition. [v0.3 of the rubric]
- **C9 Measured.** `smoke` is false wherever an output records it, and the job rc is 0 unless a block says otherwise.
- **C10 Knobs.** Each override seen in a job log or output fires a trigger (2.3): the WARNING lines of `ALLOW_FAILED_VALIDITY=1`, `ALLOW_FAILED_V4=1`, `ALLOW_UNPINNED=1` and `ALLOW_UNFROZEN_CODE=1`; a judge `override from the environment` line (`judge_override`); a `J1 flag rule override: FLAG_DELTA_MIN=` or `SM_H_BATTERIES=` line of `sm_py j1-flags` (`analysis_config_override`, value the knob name) [v0.3 of the rubric]; a battery sidecar `backend: vllm` (`battery_backend_vllm`); `steps < steps_planned` in `train_meta.json` (`lora_extra_args`).
- **C11 Prereg (G2).** The blob of `prereg/PREREG-v0.2.md` at this row's `git_sha` equals the blob at the first accepted base_card row, which records it in its note as `prereg=<blob>`. Otherwise trigger `prereg_change`. A prereg file that does not exist at the job commit (for example a `--prereg` naming a later-committed file) is precondition, so no base_card row is written without its note. [v0.3 of the rubric]

### 2.2 Outcomes, failure classes and the failure streak

**Outcome rule.** Run every check of the block plus C1 to C11. If any check fails, the outcome is REJECT, and its class is the first of these that any failed check carries: scientific, infrastructure, precondition, process, agent_code. Exception: a failed ledger witness (check LW, 2.5) makes the class process whatever else failed, since every ledger-derived check is then unreliable. [v0.2 of the rubric] If no check fails but triggers fired, the outcome is ACCEPT WITH DEVIATION when committed DEVIATIONS.md entries cover every trigger, and REJECT (process) otherwise. Otherwise the outcome is ACCEPT.

| Class | Deterministic signal (any one) | Streak |
|---|---|---|
| scientific | A validity check (V1 to V3, L* coherence) or V4 failed on a judged measured run; lora rc 3 with `status: nan_abort` | Not counted. Never resubmitted to change the result; reported descriptively or excluded as the prereg says |
| infrastructure | Compute-ledger `state` TIMEOUT, NODE_FAIL, OUT_OF_MEMORY, PREEMPTED or BOOT_FAIL; rc 143; rc 2 with a pre-flight message (`pre-flight`, `snapshot for`, `torch.cuda`, `did not become healthy`, `exited during startup`); rc 6 (base-vs-base on the base's node); a `.partial` left by a killed job; no LEDGER line; C6 hours missing | Not counted |
| precondition | rc 5; an input changed since the job ran (C4); C3 coverage missing; a job commit missing locally; J2 pass 2 unfinished; human slice missing | Not counted |
| process | An uncovered trigger; a C7 failure; a C8 change; a ledger rewrite (2.5) | Not counted. All submissions stop and `to_human/STATUS.md` names the failure |
| agent_code | Everything else: a Python traceback with a frame under `code/sm/` or `jobs/`; rc 2 with a config or revision message; a schema, count, hash or consistency failure in the outputs of a job that exited 0 | +1, at most once per slurm_job_id |

**Streak (with `--write`).** Every REJECT appends a `history` entry to `.failure_streak.json`: {timestamp, slurm_id, reason: "<stage> <base>/<run> <class> <check ids>", counted_in_streak}. An agent_code REJECT also increments `current_streak`; at `current_streak >= max_streak` (3) it sets `auto_rollback_triggered: true`, `auto_rollback_at` and `auto_rollback_reason`. An ACCEPT (with or without deviation) sets `current_streak` to 0 when its `git_sha` differs from the `git_sha` of the last counted failure (read from that failure's ledger row). accept.py never clears `auto_rollback_triggered`; under G5 only a human does.

**Effect of a REJECT.** Do not submit the stages under "Blocks" for that base (and, for per-run blocks, that run), and cancel any of their jobs already queued (`submit_bank.sh` chains stages with afterany).

### 2.3 prereg/DEVIATIONS.md (the format accept.py parses)

The file is created at the first deviation, tracked in git and append-only; a correction is a new entry naming the old id. One entry per departure from v0.2:

```
## D-001 2026-10-12
- trigger: missing_external_derivative
- stage: battery
- base: qwen3.5-9b
- run: c5_public_abliterated
- value: (required for analysis_code_change, pins_change, judge_policy_change and prereg_change: the new SHA)
- reason: no public abliterated Qwen3.5-9B exists at filing (docs/MODEL_CHOICE.md)
- prereg: Section 3
```

**Parsing.** Each entry starts with a heading matching `^## D-(\d{3}) (\d{4}-\d{2}-\d{2})$`, followed by `- key: value` lines. trigger, stage, base, run and reason are required; `*` matches anything in stage, base or run. An entry covers a fired trigger when trigger, stage, base and run match, the entry is in `git show HEAD:prereg/DEVIATIONS.md`, and `value` equals the new SHA where one is required.

**Trigger ids:** allow_failed_validity, allow_failed_v4, allow_unpinned, allow_unfrozen_code, judge_override, battery_backend_vllm, lora_extra_args, fallback_base, pins_change, prereg_change, bank_composition, missing_external_derivative, n_examples_shortfall, persona_trait_missing, capability_items, bvb_same_host, judge_policy_change, analysis_code_change, analysis_config_override, h4_external_table, hypothesis_not_evaluable, refusal_direction_not_evaluable (BC-9; covered only by an owner-signed amendment entry, see BC-9), human_gate_partial (AG-7, value `<hypothesis>:<battery>`; [v0.4.11 of the rubric, D-025]).

### 2.4 Analysis-code freeze

- **Definition.** `analysis_sha` = `<T>:<B>`, where T = `git rev-parse HEAD:code/sm/analysis` (tree id) and B = `git rev-parse HEAD:code/sm/accept.py` (blob id). It is defined only when `git status --porcelain --untracked-files=all -- code/sm/analysis code/sm/accept.py` prints nothing; otherwise it is null. Every ledger row records it.
- **Freeze row.** The first time accept.py judges a non-smoke job of stage lora, organism, battery, capability, judge_j1, judge_j2, drift or monitor_scores for a bank run (derivative other than `base`), it first appends the freeze row:
  - stage `analysis_freeze`; base and derivative `*`; that job's `slurm_job_id`; `git_sha` = HEAD; `seeds` {}; `h200_hours` 0.0; `accepted` true; note `outcome=ACCEPT; frozen at the first measured derivative run <job>`.
  - `analysis_sha`: the current value. If it is null, the outcome is REJECT (process): commit first.
  - `config_hash`: SHA-256 of the canonical JSON (sorted keys, no spaces) of {"bases": {key: revision} for the four primary bases, "judges": {"J1": revision, "J2": revision}}.
  - `output_hash`: SHA-256 of the canonical JSON of {"analysis_sha", "acceptance_md_blob" (`git rev-parse HEAD:prereg/ACCEPTANCE.md`), "judge_policies": {name: SHA-256 of `configs/judge_policies/<name>.txt`}, "rules_blob" (`git rev-parse HEAD:code/sm/analysis/rules.py`, null when absent; OPEN-11)}. [v0.2 of the rubric] The note carries the payload values after the text above (`acceptance_md_blob=<b> rules_blob=<b|none> judge_policies=<name>:<sha>,...`), so the payload can be recomputed from the ledger alone and checked against output_hash. [v0.2 of the rubric]
- **After the freeze.** Every acceptance is REJECT (process) when `analysis_sha`, the ACCEPTANCE.md blob or a judge-policy hash differs from the freeze row and no committed DEVIATIONS.md entry (trigger analysis_code_change or judge_policy_change) names the new value (the new analysis_sha, the new ACCEPTANCE.md blob, or the SHA-256 of the current policy file; one trigger per changed value). [v0.2 of the rubric] A null analysis_sha after the freeze is C8 REJECT (process). [v0.2 of the rubric] With such an entry, the outcome is ACCEPT WITH DEVIATION. AG-2 also checks the tree at the commit that produced the aggregate outputs. The owner copies the frozen `analysis_sha` into AMENDMENT A1 item 4.

### 2.5 results/ledger.jsonl

One JSON object per line. Only `accept.py --write` appends, using an exclusive `fcntl` lock, `O_APPEND`, one line and `fsync`. There is one row per judged unit: array jobs give one row per task and run; a judge job gives one row per run and judge stage; base-level stages and aggregate give one row.

| Field | Type | Content |
|---|---|---|
| slurm_job_id | string | Raw SLURM_JOB_ID from the LEDGER line (unique per array task); `local-<timestamp>` for a laptop run |
| stage | string | A Section 1 stage, or `analysis_freeze` |
| base | string | Registry key, or `*` |
| derivative | string | run_id, `base`, or `*` |
| config_hash | string or null | SHA-256 of the config file named in the block |
| git_sha | string | 40 hex (C2) |
| analysis_sha | string or null | 2.4, computed at acceptance time |
| seeds | object | {name: int} (C5) |
| output_hash | string | C4 |
| h200_hours | number | C6 |
| accepted | bool | true for ACCEPT and ACCEPT WITH DEVIATION |
| timestamp | string | ISO 8601 with UTC offset; the time of acceptance |
| note | string | `outcome=<ACCEPT or ACCEPT_WITH_DEVIATION or REJECT>[ class=<c>][ checks=<ids>][ deviations=<D-ids>][ corrects=<row id>]; <text>` |

**Append-only.** Rows are never edited, reordered or deleted. A row's id is the SHA-256 of its line without the newline. A correction (a human reclassification, a re-acceptance after `sm_ledger_add`, an accepted re-run) is a new row whose note carries `corrects=<row id>`; accept.py adds it whenever a row with the same (slurm_job_id, stage, base, derivative) exists. [v0.2 of the rubric] Readers take the last row per (slurm_job_id, stage, base, derivative).

**Witness.** `results/.ledger_state.json` holds {n_rows, prefix_sha256 (the hash of the first n_rows lines), updated}. Every `--write` and `--verify-ledger` first checks the prefix; `--write` then appends and updates the state. Rows appended after the last witness update (a crash between the append and the state write) are tolerated; changed, removed or reordered witnessed rows are not. [v0.2 of the rubric] A tolerated row must validate and equal the `ledger_row` or `freeze_row` of an acceptance report marked `written` or `append_pending` (accept.py saves the report before appending); any other tail row fails the witness and is never folded into it. When HEAD tracks `results/ledger.jsonl`, the committed ledger must be a byte prefix of the working one; when HEAD tracks `results/.ledger_state.json`, its `n_rows` may not exceed the current one; a tracked file that is missing fails. [v0.3 of the rubric] A mismatch is REJECT (process) for every stage until the owner restores the file. The ledger ships with the preprint and holds no completion or judge text.

### 2.6 Implementation notes [v0.2 of the rubric]

- **Missing fields.** A check that needs a field another module adds after commit 5acbc0a (judge identity, completion_sha256 on label rows, adapter_sha256 in battery sidecars, the smoke artifact, meta.analysis_tree, results/human/kappa.json) fails with the detail `field missing: <name>` and class precondition (backfill or re-run), never with a crash. Two deterministic derived paths exist: SM-1 to SM-3 from the job log when no smoke artifact exists, and BT-3 from the adapter weights file the sidecar's `meta.adapter_path` names (when `adapter_config_sha256` verifies). J1-9 has none: a label row without `completion_sha256` cannot be tied to its completion after a resume, and the judge re-scores such rows on its next run.
- **Prereg file.** C11 and AG-3 read `prereg/PREREG-v0.2.md` unless `--prereg` (or `SM_PREREG_PATH`) names the filed version; the choice must stay fixed for the study, since C11 compares blobs with the first base_card row. Malformed outputs (wrong type, unparsable JSON) fail the check as agent_code. An internal error of accept.py exits 2 and is never an outcome.
- **Rubric v0.3 changes (review fixes).** [v0.3 of the rubric] C7c searches escaped and per-value text, a wider scope, and fails on archives under results/; the witness binds the ledger committed at HEAD and only tolerates tail rows that match a report; C8 also checks the job commit's analysis tree; J2-3/J2-4 re-derive the J2 status with `sm.analysis.rules`; AG-7 hard-codes kappa_full and checks judge, gated, blinding counters, labels_sha256 and the J1 pin; J1-5, J2-7 and AG-1 re-verify the upstream unit's accepted output_hash; J1-9 hashes the completion text; C3 binds code/ and jobs/; C10 reads the J1 flag override lines; C11 uses the first accepted base_card row and fails softly when the prereg file is missing at the job commit.
